# 1.3 Local SDK Component Mapping

> 🎯 *"These libraries share the same in-process state."*

## Four core components

The signature headers do not appear out of thin air; they are generated by a group of native libraries inside the App. The mapping given by the original is:

| SDK library | Responsibility | Corresponding output |
|---|---|---|
| `libmetasec_ml.so` (MSSDK) | device collection, token issuance, seven signature headers | X-Gorgon / X-Ladon / SDI token / Perseus |
| `libbdsword.so` | SwordCipher, stats_collect encoding | app_log / stats data bodies |
| `libbdbadger.so` (v4.0) | BadgerCipher, dtrait form | `dtrait_pk1` |
| ttNet / Cronet | network transport stack | TLS fingerprint, HTTP/2, cronet version number |

### MSSDK (`libmetasec_ml.so`)

This is the most central library. It is responsible for:

- device information collection;
- token issuance (SDI token);
- the seven signature headers (including at least Gorgon, Ladon, and Perseus).

It is not a "pure function library", but a runtime with internal state: it initializes a seed at startup, maintains the clock, caches tokens, and stores the session UUID.

### Sword (`libbdsword.so`)

Responsible for `SwordCipher` and `stats_collect` encoding, producing `app_log` / `stats` data bodies.

This corresponds to behavior-layer reporting: first-launch tracking, page events, impression events, and so on.

### Badger (`libbdbadger.so`, v4.0)

Responsible for `BadgerCipher` and the `dtrait` form, producing `dtrait_pk1`.

`dtrait` is another structured encoding of device information. The original stresses that it and SDI are **two independent encodings of the same fact**, which the server can cross-compare for consistency. This is also why both algorithms must be reproduced completely, rather than only one.

### ttNet / Cronet

Responsible for network transport, determining:

- the TLS fingerprint;
- HTTP/2 behavior;
- the cronet version number.

This layer does not generate signature headers, but it determines "whether this link looks like a real client".

## Shared process state

The original contains a very important statement:

> These libraries share the same in-process state — clock origin, session UUID, KD storage, token cache. If a simulation computes each header separately without sharing state, then even if every header looks valid on its own, the combination will be judged anomalous.

This can be organized into a "state table":

| State | Maintained by | Consumed by | Lifecycle |
|---|---|---|---|
| Clock origin | MSSDK | Medusa f17, Perseus sts | process / session |
| Session UUID | MSSDK | Medusa, Perseus | generated on the first request of a session, fixed within the session |
| KD | MSSDK | Perseus checksum | process-wide shared, persisted across requests |
| token cache | MSSDK | SDI / Perseus | device + App version |
| Startup seed | MSSDK | Perseus FL | generated at SDK startup |

## Implications for a simulated implementation

If you implement it as "one independent function per header", you will usually run into three classes of problems:

1. **Time inconsistency**: each header takes the current time separately, and millisecond-level differences cause signature mismatches.
2. **Session inconsistency**: session_uuid is regenerated on every request, so the server sees "the same device constantly switching sessions".
3. **State inconsistency**: KD is generated independently on every request, exposing the timing characteristics of the checksum.

The correct mental model is: **one process has one shared SDK state, and all headers derive from it**.

<div class="callout note"><span class="callout-title">🔑 Key conclusion</span>
Design the state container before implementing the algorithms. The lifetime of each state (process / session / request) determines which values must be persisted and which must be updated per request.
</div>

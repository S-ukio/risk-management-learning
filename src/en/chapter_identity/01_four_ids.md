# 2.1 The Four Device Identifiers

> 🎯 *"The essence of the registration flow is exchanging two of the four local identifiers for the other two issued by the server."*

## The Four Identifiers

| Identifier | Generator | Lifecycle | Source of trust |
|---|---|---|---|
| `device_id` | Assigned by the server (after successful registration) | Device-level, long-term | Issued by the server; cannot be forged locally |
| `iid` (install_id) | Assigned by the server | Install-level | Returned by the registration chain |
| `openudid` | Generated by the client | Device-level, persisted | Locally random; first reported at registration |
| `cdid` | Generated by the client (uppercase UUID) | Install-level | Locally random |

## One-Way Trust

The source's summary:

> The trust relationship is one-way: `openudid` / `cdid` are **local declarations**, while `device_id` / `iid` are **the server's trust in those declarations**.

This means:

- The client can "claim" to be a given `openudid` / `cdid`;
- But `device_id` / `iid` can only be issued by the server;
- Through the registration chain, the server binds the "local declaration + complete device fingerprint" to a "server-side identity".

## Registration Exchange

Registration can be understood as an exchange:

```text
Local declarations                         Server-issued
┌────────────────────────┐                 ┌──────────────────────┐
│                        │                 │                      │
│ openudid               │   ──────────▶   │ device_id            │
│ cdid                   │  registration   │ iid                  │
│ complete device        │     request     │ sec_device_token     │
│ fingerprint            │   ◀──────────   │                      │
│                        │     response    │                      │
└────────────────────────┘                 └──────────────────────┘
```

After the exchange:

- `openudid` / `cdid` remain on the local device;
- `device_id` / `iid` become the official identity for subsequent requests;
- `sec_device_token` becomes the device-level signing credential.

## Practical Points

### 1. Subsequent Requests Must Match the Registration Result

In the query of every subsequent request, `device_id` / `iid` must match the registration result.

The source specifically notes: **the signature entry layer validates `device_id` as 14–19 decimal digits.**

This means:

- `device_id` is not an arbitrary string;
- Both length and character set are constrained;
- A forged ID with the wrong format is rejected at the signature entry, not later at the business layer.

### 2. `sec_device_token` Must Be Persisted

`sec_device_token` is the server's signing credential for the device:

- It participates in the construction of the Perseus / Medusa context;
- It must be persisted;
- It must be sent back within the session.

It is not one-off; it is a long-lived device-level credential.

### 3. Luckydog Credentials Are Stored per Session

The source notes: the `act_base` / `act_data` / `act_token` returned by `luckydog` are likewise stored and returned per session.

They are **activity credentials issued by the server** and involve no local recovery algorithm—that is, the client does not need to "compute" them, only to store and return them correctly.

<div class="callout note"><span class="callout-title">🔑 Key Takeaway</span>
The core of device identity is not "generating an ID" but "maintaining a consistent identity state across requests". device_id, iid, sec_device_token, and act_* each have their own lifecycle and must not be mixed.
</div>

## State Lifecycle Quick Reference

| Value | Lifecycle | Cross-session | Notes |
|---|---|---|---|
| `openudid` | Device-level | Yes | Reported at first registration |
| `cdid` | Install-level | Yes (within the install) | Uppercase UUID |
| `device_id` | Device-level, long-term | Yes | 14–19 decimal digits |
| `iid` | Install-level | Yes (within the install) | Returned at registration |
| `sec_device_token` | Device-level | Yes | Server signing credential |
| `act_base` / `act_data` / `act_token` | Session-level | Per session | Server activity credentials |

# 4.4 f17 时钟槽、会话结构与八分支疑问

> 🎯 *“第一秒钉住起点，后续 elapsed 单调增长。”*

## f17 时钟槽

原文：

> f17 时钟槽：报告内的时钟采样，含 f17_base_ns、ticks、请求序号。

三个组成部分：

| 字段 | 含义 |
|---|---|
| `f17_base_ns` | 时钟基准（纳秒） |
| `ticks` | 采样计数 |
| 请求序号 | 当前请求在会话中的序号 |

### 单调性要求

原文：

> 要求单调性——跨请求不回退、不重复，这是检测时钟回拨 / 多开的核心手段。

三个约束：

1. **不回退**：后一个请求的时钟值必须 ≥ 前一个；
2. **不重复**：不能两个请求用同一个时钟值；
3. **跨请求持久化**：时钟状态不能在请求之间丢失。

### 生命周期

原文：

> 时钟生命周期需要跨请求持久化：第一秒钉住起点，后续 elapsed 单调增长。

可以画成：

```text
请求 1：base = T0, elapsed = 0
请求 2：base = T0, elapsed = Δ1   (Δ1 > 0)
请求 3：base = T0, elapsed = Δ2   (Δ2 > Δ1)
...
```

注意：`base` 不变，`elapsed` 单调增长。如果每个请求都重设 `base`，服务端会看到“会话起点不断漂移”。

### 41.2 的差异

原文：

> 41.2 的长帧对时钟槽位编排与旧版短帧不同，但单调性约束两版一致。

含义：

- 槽位怎么排、放在哪，41.2 与旧版不同；
- 但“不回退、不重复”的约束不变；
- 实现时不能因为换了长帧就放松单调性。

## 会话结构

### `medusa_session_uuid`

原文：

> `medusa_session_uuid` 在会话首请求生成并固定；`req_f2` 等请求级槽位逐请求更新。

| 字段 | 生命周期 | 更新时机 |
|---|---|---|
| `medusa_session_uuid` | 会话级 | 会话首请求生成，之后固定 |
| `req_f2` 等 | 请求级 | 每个请求更新 |

### 注册体中的时钟组

原文：

> 注册体中预埋的时钟组在此消费。

也就是说，3.3 中的 `medusa_clock_origin` / `medusa_session_ms` / `medusa_elapsed_ms` / `medusa_session_uuid` 不是注册完就没用了，而是会在后续 Medusa 报告中被消费。

### 41.2 的外层检查字

原文：

> 41.2 报告体外层新增检查字（由 query SM3 低位与 field13 低位组合而成），进一步绑定请求内容与报告。

含义：

- 41.2 的报告体外层多了一个检查字；
- 它由 query SM3 的低位与 field13 的低位组合；
- 作用是把“请求内容”和“报告”绑定得更紧。

<span class="badge gap">原文缺图</span> 检查字的具体位宽、组合方式、校验规则在原文中没有展开，列入待研究问题。

## 八分支结构：一个需要核对的段落

原文在 4.3 末尾出现了这样一段：

> 八个分支的构成：
>
> 分支选择：`slot = int(khronos) & 7`，**只由 khronos 低 3 位决定，与正文长度和内容无关**。

并给出下表：

| slot | 算法形态 | 特征 |
|---|---|---|
| 0 | 魔改 AES-CBC（2 轮） | S-box 异或 `0x3d` |
| 1 | 魔改 AES-CBC（2 轮） | S-box 异或 `0x33` |
| 2 | 魔改 AES-CBC（2 轮） | S-box 异或 `0x3b` |
| 3 | 魔改 AES-CBC（2 轮） | S-box 异或 `0x39` |
| 4 | 仿射 SPN（24 轮） | 固定仿射参数表 |
| 5 | 第二虚拟机核 | 主状态生成 + 两次 24 轮归约 |
| 6 | 魔改 SM4 形态（24 轮） | S-box 异或 `0x17` |
| 7 | 魔改 SM4 形态（24 轮） | S-box 异或 `0x1f` |

### 结构规律

原文：

> 结构规律：`slot % 4` 决定族（AES-CBC / 仿射 SPN / VM / SM4），`slot // 4` 决定族内变体（S-box 异或值 `0x39` 与 `0x3d`、`0x17` 与 `0x1f` 成对）。四个 AES 分支共享轮结构只差一个常数异或；两个 SM4 分支同理。

### 正反向

原文：

> 每个分支都提供正向（19B → 32B MAC）与逆向（32B → 19B）两个方向；AES/SM4 形态分支在内部将 19 字节输入补齐 13 个 `0x0d` 凑成两块。逆变换后要求重算正向比对，防伪 MAC。

### ⚠️ 归属疑问

这一段与前面的 field13 描述存在明显冲突：

- 前面说 field13 有 **16 个分支**，按 `slot & 15` 选择；
- 这一段说 **8 个分支**，按 `slot & 7` 选择；
- 前面说输出 **20B**，这一段说正向 **19B → 32B MAC**。

可能的解释：

1. 它描述的是另一个组件（不是 field13），只是原文排版时放在了 4.3 末尾；
2. 它是某个旧版本 / 子功能的算法，与 field13 并行存在；
3. 原文在版本之间混用了“分支”一词，实际指两套不同的东西。

<span class="badge gap">原文缺图</span> 原文没有说明这八个分支属于哪个头、哪个版本。本笔记**不猜测归属**，只保留表格与疑问。

> 📌 这是 5.2 待研究问题的第一优先级：先确认“八分支”究竟属于谁，再谈复现。

## 状态生命周期总表

| 状态 | 作用域 | 生命周期 | 约束 |
|---|---|---|---|
| `f17_base_ns` | 会话 | 跨请求持久 | 固定不变 |
| `ticks` | 请求 / 会话 | 请求级更新 | 单调 |
| 请求序号 | 会话 | 递增 | 不重复 |
| `medusa_session_uuid` | 会话 | 首请求生成 | 固定 |
| `req_f2` | 请求 | 每请求更新 | 与请求绑定 |
| 外层检查字（41.2） | 请求 | 每请求生成 | 绑定 query + field13 |

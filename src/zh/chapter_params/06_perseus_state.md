# 4.6 X-Perseus：KD、校验和与 protobuf

> 🎯 *“KD 的语义是进程内共享、生命周期隔离。”*

## 进程环境

原文给出一组进程环境字段：

```json
{
  "pid": 20033,
  "ppid": 886,
  "thread_pointer": 498090588864,
  "module_base": 497986002944,
  "jni_call_void": 505028537152
}
```

| 字段 | 含义 |
|---|---|
| `pid` | 进程 ID |
| `ppid` | 父进程 ID |
| `thread_pointer` | 线程指针 |
| `module_base` | 模块基址 |
| `jni_call_void` | JNI 调用地址 |

原文：

> 这些地址特征是环境一致性校验的一部分。

## 地址偏移规律

原文的观察：

> `token_address`(512296902576) − `module_base`(497986002944) = 4310889632 ≈ `0x4000000` 量级的偏移规律，`thread_pointer` 与 `module_base` 同样满足基址偏移关系。

<div class="callout warn"><span class="callout-title">⚠️ 笔记核对：这里的量级对不上</span>
按原文给出的数值直接计算：

- `512296902576 − 497986002944 = 14310899632 = 0x354FEFFB0`，约 **13.3 GiB**；
- `0x4000000` 只有 **64 MiB**，两者相差约 213 倍。

`thread_pointer − module_base = 104585920 = 0x63BDAC0`，约 **99.7 MiB**。

因此，原文的“≈ 0x4000000 量级”可能：
1. 少写了若干十六进制位（例如本意是 `0x400000000` 量级）；
2. 或数值单位 / 字段含义与字面不同；
3. 或示例数值与描述来自不同版本。

**本笔记不擅自修正原文结论**，只记录计算结果，列入[待研究问题](../chapter_reflection/02_open_questions.md)。
</div>

| 字段 | 示例值 | 说明 |
|---|---|---|

| `do` | 1 | 标志位 |

原文：

> `pd`（cmr）与 `fkd`（cmr2）写入报告，服务端解密后重算比对。

## KD 是什么

原文：

> KD 是 SDK 进程内的键值状态，参与会话校验。

来源两条路径：

1. **SDK provider 存储文本恢复**：存储文本按十进制解析为 `uint32`；
2. **默认初值 0**：冷启未持久化状态。

示例向量中 `kd=0`，即冷启场景。

- `session_uuid = "861775c1-5ed4-47f2-b474-2c51dcd9e43e"`；
- 得到 `pd = 815239457`、`fkd = 2665330607`。

## 关键一致性要求

原文：

> KD 的语义是进程内共享、生命周期隔离——同一 App 进程内跨请求共享同一 KD 值（第一请求写、后续请求读同一值），不同 App 身份（aid）之间隔离，SDK 进程重启后恢复自存储文本。若模拟实现每个请求独立生成 KD，校验和的时序特征即暴露。

拆成四条：

| 要求 | 含义 |
|---|---|
| 进程内共享 | 同一进程的多个请求读同一个 KD |
| 生命周期隔离 | 不同 aid 之间不能共享 |
| 重启恢复 | SDK 进程重启后从存储文本恢复 |
| 禁止每请求生成 | 每个请求独立生成 KD 会暴露时序特征 |

## protobuf 结构

原文：

```text
report.field1 = 1
report.field3 = {
  "6":  "v04.10.05.02-bugfix",   # SDK 构建版本
  "7":  40066,
  "14": "41.2.0",                # App 版本
  "15": 1772,
  "18": 3285352954,
  "19": 3590681842,
  "20": 992990262394
}
report.field4 内嵌 JSON = {
  上面会话校验和那组字段 + "fl" / "lp" / "tk"
}
```

| 字段号 | 示例值 | 说明 |
|---|---|---|
| `field1` | 1 | 固定值 |
| `field3.6` | `v04.10.05.02-bugfix` | SDK 构建版本 |
| `field3.7` | 40066 | 版本相关 |
| `field3.14` | `41.2.0` | App 版本 |
| `field3.15` | 1772 | 版本相关 |
| `field3.18` | 3285352954 | 未知 |
| `field3.19` | 3590681842 | 未知 |
| `field3.20` | 992990262394 | 未知 |
| `field4` | JSON | 校验和 + fl / lp / tk |

## session UUID 与 token address

原文：

> `session_uuid`：由 SDK 内部 RNG 状态派生，会话首请求生成后缓存，同一会话内不变化。

> `token_address`：进程内存地址特征，与模块基址关联，满足基址 + 固定量级偏移的规律。模拟时随机生成但必须保持与 `module_base` 的偏移关系，独立随机的地址是环境检测的特征之一。

两条要点：

1. `session_uuid` 是会话级，首请求生成后固定；
2. `token_address` 不能独立随机，必须与 `module_base` 保持偏移关系。

<div class="callout note"><span class="callout-title">🔑 关键结论</span>
Perseus 的一致性不只体现在字段值，还体现在“状态的生命周期”和“地址的相对关系”。KD 每请求生成、session_uuid 每请求变化、token_address 独立随机，都是典型暴露点。
</div>

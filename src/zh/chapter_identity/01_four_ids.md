# 2.1 设备标识四件套

> 🎯 *“注册流程的本质，就是拿本地四件套中的两个，换取服务端签发的另外两个。”*

## 四个标识

| 标识 | 生成方 | 生命周期 | 信任来源 |
|---|---|---|---|
| `device_id` | 服务端分配（注册成功后） | 设备级，长期 | 服务端签发，不可本地伪造 |
| `iid`（install_id） | 服务端分配 | 安装级 | 注册链路返回 |
| `openudid` | 客户端生成 | 设备级，持久保存 | 本地随机，注册时首次上报 |
| `cdid` | 客户端生成（UUID 大写） | 安装级 | 本地随机 |

## 单向信任

原文的总结：

> 信任关系是单向的：`openudid` / `cdid` 是**本地声明**，`device_id` / `iid` 是**服务端对声明**。

这意味着：

- 客户端可以“声称”自己是某个 `openudid` / `cdid`；
- 但 `device_id` / `iid` 只能由服务端签发；
- 服务端通过注册链路，把“本地声明 + 完整设备指纹”绑定到“服务端身份”上。

## 注册交换

可以把注册理解成一次交换：

```text
本地声明                        服务端签发
┌──────────────┐               ┌──────────────────┐
│ openudid     │  ──────────▶  │ device_id        │
│ cdid         │   注册请求     │ iid              │
│ 完整设备指纹  │               │ sec_device_token │
└──────────────┘  ◀──────────  └──────────────────┘
                     注册响应
```

交换完成后：

- `openudid` / `cdid` 仍然保留在本地；
- `device_id` / `iid` 成为后续请求的正式身份；
- `sec_device_token` 成为设备级签名凭证。

## 实践要点

### 1. 后续请求必须与注册结果一致

后续所有请求的 query 中，`device_id` / `iid` 必须与注册结果一致。

原文特别提到：**签名入口层对 `device_id` 有 14～19 位纯数字的合法性校验**。

这意味着：

- `device_id` 不是任意字符串；
- 长度和字符集都有约束；
- 伪造一个格式不对的 ID，会在签名入口就被拒绝，而不是等到业务层。

### 2. `sec_device_token` 必须持久化

`sec_device_token` 是服务端对设备的签名凭证：

- 参与后续 Perseus / Medusa 的上下文构建；
- 必须持久化；
- 必须在会话中回传。

它不是“一次性的”，而是设备级的长期凭证。

### 3. luckydog 凭证按会话保存

原文提到：`luckydog` 返回的 `act_base` / `act_data` / `act_token` 同样按会话保存回传。

它们是**服务端下发的活动凭证**，不涉及本地恢复算法——也就是说，客户端不需要“算”出它们，只需要正确保存和回传。

<div class="callout note"><span class="callout-title">🔑 关键结论</span>
设备身份的核心不是“生成一个 ID”，而是“维持一套跨请求一致的身份状态”。device_id、iid、sec_device_token、act_* 都有各自的生命周期，不能混用。
</div>

## 状态生命周期速查

| 值 | 生命周期 | 是否跨会话 | 备注 |
|---|---|---|---|
| `openudid` | 设备级 | 是 | 首次注册上报 |
| `cdid` | 安装级 | 是（安装内） | UUID 大写 |
| `device_id` | 设备级，长期 | 是 | 14～19 位纯数字 |
| `iid` | 安装级 | 是（安装内） | 注册返回 |
| `sec_device_token` | 设备级 | 是 | 服务端签名凭证 |
| `act_base` / `act_data` / `act_token` | 会话级 | 按会话 | 服务端活动凭证 |

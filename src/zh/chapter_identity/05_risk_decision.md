# 2.5 指纹与风控决策

> 🎯 *“empty 不是失败，而是新设备冷启后的正常阶段。”*

## 四种状态

原文把搜索类请求的结果分为四个状态，并以此作为风控判定边界：

| 状态 | 含义 | 风控解读 |
|---|---|---|
| `success` | 返回了视频 / 用户结果 | 设备可信 |
| `empty` | 请求成功但返回空页 | 轻度降权，设备标签尚未完全建立 |
| `blocked` | 需要验证或限流 | 指纹 / 行为被标记 |
| `error` | 请求或响应异常 | 协议层错误，先查签名再查指纹 |

## `empty` 为什么最容易被误判

原文有一句很重要的提醒：

> empty 是最容易被误判的状态：它不是失败，而是新设备冷启后的正常阶段。

新手常把“没有返回数据”当成“请求失败”，于是：

- 反复重试；
- 频繁更换设备参数；
- 误以为签名算法错了。

实际上，新设备刚注册、信任分还没建立时，返回空页是预期行为。频繁重试反而会让行为层更像脚本。

## 正确的判断方式

原文建议：

> 判断设备是否可用应看 `search_ok`（有结果或正常空页均为真），而非单纯看有没有数据。

可以把判定逻辑写成伪代码：

```text
if response.status == success:
    search_ok = true
elif response.status == empty:
    search_ok = true     # 正常空页，不代表设备不可用
elif response.status == blocked:
    search_ok = false    # 指纹或行为被标记
else:  # error
    search_ok = false    # 先查签名，再查指纹
```

## 状态与排查顺序

| 状态 | 先查什么 | 再查什么 |
|---|---|---|
| `success` | — | — |
| `empty` | 是否新设备 / 信任分不足 | TrustChain 是否预热 |
| `blocked` | 指纹一致性 | 行为时序、环境检测 |
| `error` | 签名算法 | 参数格式、版本配置 |

<div class="callout warn"><span class="callout-title">⚠️ 排查顺序很重要</span>
看到 `error` 先查指纹，往往会白忙一场——多数 `error` 是签名或参数格式问题。反过来，看到 `blocked` 只查签名，也会忽略真正的指纹矛盾。
</div>

## 与三层模型的对应

| 状态 | 最可能出问题的层 |
|---|---|
| `empty` | 行为层（信任分不足） |
| `blocked` | 设备层 / 行为层 |
| `error` | 协议层（签名、参数、版本） |

这也解释了为什么第 1 章要强调“三层是 AND”：不同状态对应不同的失败层，排查时必须先定位层，再定位字段。

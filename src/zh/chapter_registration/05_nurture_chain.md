# 3.5 养号与激活链路

> 🎯 *“全部请求在 1 秒内打完，本身就是异常特征。”*

## 注册只是拿到身份

原文的定位很清楚：

> 注册只是拿到身份，行为冷启链路包含：

也就是说，注册成功 ≠ 设备可用。后面还有一条“行为冷启”链路。

## 四个步骤

| 步骤 | 动作 | 内容 |
|---|---|---|
| 1 | `app_log` 上报 | 首启清单，不携带指纹运行结果 |
| 2 | `stats_collect` | 行为统计（Sword 编码），启动、页面、曝光事件 |
| 3 | `app_alert_check` | 拉取服务端下发配置并解析，决定后续行为开关 |
| 4 | 补充上报 | `log_settings`、权限事件等 |

### 1. `app_log`

- 首启清单；
- **不携带指纹运行结果**；
- 指纹是后续步骤，不能提前混进首启日志。

### 2. `stats_collect`

- 行为统计；
- 使用 Sword 编码；
- 内容为启动、页面、曝光事件。

### 3. `app_alert_check`

- 拉取服务端下发配置；
- 解析配置；
- 决定后续行为开关。

这一步说明：服务端不是“被动收数据”，而是会下发配置来引导客户端行为。客户端的后续动作应该受这份配置影响。

### 4. 补充上报

- `log_settings`；
- 权限事件等。

## 时序会被建模

原文的关键判断：

> 行为链路的时序同样被建模：服务端对“注册后多长时间内做了什么”有预期分布。

这意味着服务端不只看“你做了什么”，还看“你在多久内做的”。

### 为什么 1 秒内打完反而异常

原文：

> 全部请求在 1 秒内打完的注册 + 养号链路，本身就是异常特征——真实设备的链路天然带秒级间隔。

真实设备的链路包含：

- 网络往返（RTT）；
- 页面渲染；
- 用户交互；
- 系统调度；
- 服务端响应等待。

这些因素天然产生秒级间隔。把整条链路压缩到 1 秒内，说明：

- 没有等待页面；
- 没有真实交互；
- 没有按服务端响应推进。

这本身就是“脚本”的特征。

## 行为冷启的正确节奏

可以把链路理解成“有依赖的异步流程”：

```text
注册成功
  │
  ├─ app_log（首启清单，不含指纹结果）
  │      │  等待网络 + 渲染
  │      ▼
  ├─ stats_collect（启动 / 页面 / 曝光）
  │      │  等待事件产生
  │      ▼
  ├─ app_alert_check（拉配置）
  │      │  根据配置决定后续
  │      ▼
  └─ 补充上报（log_settings / 权限事件）
```

每一步都应该：

- 等待前一步完成；
- 等待真实的页面 / 事件；
- 根据服务端响应决定下一步。

<div class="callout warn"><span class="callout-title">⚠️ 不要“优化”掉间隔</span>
把间隔压缩到最小并不是优化，而是暴露。真实设备的链路本来就有等待，脚本才追求“零延迟”。
</div>

# 3.2 注册链路分解

> 🎯 *“顺序即契约。”*

## 六步链路

原文给出的完整冷注册链路（按严格顺序）：

| 步骤 | 接口 / 动作 | 产出 |
|---|---|---|
| 1 | `device_register` | 获取 `device_id` / `iid`（`klink.amemv.com`） |
| 2 | `device_report` | Perseus 设备报告 |
| 3 | `app_log` | 首启埋点（Sword 编码） |
| 4 | `get_token` | SDI token 下发 |
| 5 | `activate` / `activate_record` | 激活状态上报 |
| 6 | `birth()` | 养号链路（见 3.5） |

```text
1. device_register  → device_id / iid
2. device_report    → Perseus 设备报告
3. app_log          → 首启埋点（Sword 编码）
4. get_token        → SDI token
5. activate / activate_record → 激活状态
6. birth()          → 养号链路
```

## 顺序为什么重要

原文的总结：

> 顺序即契约：app_log 必须在指纹运行前发送首启清单（不可携带指纹运行结果）；birth 的 alert 报告必须对首次启动报文签名；ri 报告使用本机参数。乱序不必然失败，但服务端会记录行为时序作为长期画像，乱序设备的后续请求权重会降低。

拆开看，这里有三个具体约束：

### 1. `app_log` 必须在指纹运行前

- 首启清单不能携带“指纹运行结果”；
- 也就是说，`app_log` 记录的是“刚启动时看到了什么”，而不是“跑完采集后总结出来的东西”。

### 2. `birth` 的 alert 报告必须对首次启动报文签名

- `birth` 不是随便发一个“我出生了”；
- 它要对**首次启动报文**签名；
- 这意味着首次启动报文必须被保存下来，供后续签名使用。

### 3. `ri` 报告使用本机参数

- 与 2.3 的提醒一致；
- `ri` 内容必须来自本机采集，不能从外部传入。

## 乱序的后果

原文说“乱序不必然失败”，这很容易被误解为“乱序无所谓”。实际含义是：

- 服务端不会因为一次乱序就立刻拒绝；
- 但会把时序记录进长期画像；
- 后续请求的权重会降低；
- 降权是累积的，不是单次判定。

这就像信用分：一次迟到不会立刻封号，但会留下记录。

## 一个反例：1 秒内打完

原文在 3.5 提到：

> 全部请求在 1 秒内打完的注册 + 养号链路，本身就是异常特征——真实设备的链路天然带秒级间隔。

所以，**“快”不是优点**。真实设备的链路有：

- 网络往返；
- 页面渲染；
- 用户交互；
- 系统调度。

这些都会自然产生秒级间隔。把六步压缩到 1 秒内，反而暴露了“这不是真实设备”。

## 链路状态图

```text
[1] device_register
      │  device_id / iid
      ▼
[2] device_report ──▶ Perseus
      │
      ▼
[3] app_log ─────────▶ 首启埋点（不含指纹结果）
      │
      ▼
[4] get_token ───────▶ SDI token
      │
      ▼
[5] activate / activate_record
      │
      ▼
[6] birth() ─────────▶ 养号链路
```

每一步都消费前一步的状态，并把新状态写入共享容器。

<div class="callout note"><span class="callout-title">🔑 关键结论</span>
注册链路的正确性 = 顺序正确 + 时序自然 + 状态连续。只满足其中一项，不足以通过行为层。
</div>

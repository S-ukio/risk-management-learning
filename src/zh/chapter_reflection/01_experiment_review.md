# 5.1 实验复盘：400 台设备与 85%

> 🎯 *“这里我大概跑了注册 400 多设备，其中能跑搜索、评论的在 350 左右，成功率在 85%。”*

## 原文数据

原文最后给出的复盘：

> 这里我大概跑了注册 400 多设备，其中能跑搜索、评论的在 350 左右，成功率在 85%，若大佬们有上号风控相关经验或协议发帖、下单都可以交流学习。

整理成表：

| 指标 | 数值 |
|---|---|
| 注册设备数 | 400+ |
| 能跑搜索 / 评论 | 约 350 |
| 成功率 | 约 85% |

> ⚠️ **说明**：这是原文作者报告的结果，本笔记未独立复现，也无法验证其统计口径。这里只讨论它揭示的方法论，不把它当作可复制的操作指南。

## 85% 说明了什么

### 1. 单点正确不够，端到端一致才够

如果七个签名头、SDI、dtrait、TicketGuard 都能单独算对，成功率应该接近 100%。实际只有 85%，说明失败的 15% 主要不是“算法不会”，而是：

- 状态不一致（时钟、KD、session_uuid）；
- 版本配置不匹配；
- 环境检测命中（root、Frida、模拟器、VPN）；
- 指纹组合矛盾；
- 时序不自然。

这与第 1 章的结论一致：**最常见的失败是状态不自洽**。

### 2. 链路完整性比单字段精度更重要

原文在 2.3 提到“服务端容忍部分字段缺失，但不容忍链路中断”。85% 的成功率也说明：

- 少量字段缺失可以容忍；
- 链路中断、顺序错误、时序异常会被累积降权；
- 端到端跑通比“每个字段都完美”更重要。

### 3. 失败样本比成功样本更有信息量

如果能拿到那 15% 的失败样本，按第 2.5 的四种状态分类：

| 状态 | 可能原因 |
|---|---|
| `empty` | 信任分不足、预热缺失、新设备冷启 |
| `blocked` | 指纹矛盾、环境检测、行为异常 |
| `error` | 签名错误、版本不匹配、参数格式 |

这比“成功率 85%”这个数字本身更有价值。

## 方法论启示

| 启示 | 对应章节 |
|---|---|
| 先保证状态一致，再抠算法 | 1.1、1.3 |
| 版本是全局配置，不是字符串 | 1.4、4.8 |
| 时钟、KD、session_uuid 必须跨请求持久化 | 3.1、4.4、4.6 |
| 行为时序要自然，不要追求零延迟 | 3.5 |
| 用四种状态定位失败层，而不是盲目重试 | 2.5 |
| 原文缺图处不要猜，先列问题 | 5.2 |

## 不要误读的地方

原文作者在结尾说“若大佬们有上号风控相关经验或协议发帖、下单都可以交流学习”。这句话容易被误读为“这是一份操作指南”。

实际上：

- 原文没有给出批量注册、养号、发帖、下单的步骤；
- 它分析的是**风控参数的构成与版本差异**；
- 本笔记也不提供任何操作步骤。

<div class="callout warn"><span class="callout-title">⚠️ 边界</span>
“理解风控如何工作”与“批量绕过风控”是两件事。前者可以用于防御、评估与合规测试；后者可能违反平台条款与法律。本笔记只讨论前者。

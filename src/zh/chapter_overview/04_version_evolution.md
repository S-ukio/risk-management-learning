# 1.4 版本演进：39.4 → 41.2

> 🎯 *“从 41.1 开始算法发生了一些改动。”*

## 原文的版本范围

原文分析的是 **39.4 ～ 41.2** 之间的不同版本，重点介绍 41.1 起的更新点和差异。

| 版本段 | 状态 | 原文着墨 |
|---|---|---|
| 39.4 ～ 40.x | 旧版短帧链路 | 作为对照 |
| 41.0 | 过渡版本 | 未展开 |
| 41.1 ～ 41.2 | v412 长帧、khronos 驱动、Perseus | 重点 |

> <span class="badge gap">原文缺图</span> 原文没有给出 41.0 的具体变化，本笔记不补猜。

## 41.1 前后的核心差异

### 差异一：Medusa 从短帧切到长帧

- **旧版（≤40.x）**：短帧链路，流程是“异或流 → 种子异或 → 魔改 AES → 帧封装”。
- **新版（41.1/41.2）**：v412 长帧链路，field13 的分支选择机制完全改变。

### 差异二：field13 从“内容驱动”改成“khronos 驱动”

| 维度 | 旧版 ≤40.x | 新版 41.1/41.2 |
|---|---|---|
| slot 选择 | 52B 内容混合函数迭代后取低 4 位 | `slot = (khronos ^ 52) & 15` |
| 分支族 | SHA-256 / Whirlpool / MD5 三族 | SHA-256 / Whirlpool / BLAKE2b / MD5 四族 |
| 分支与输入关系 | 同内容恒同分支 | khronos 变 → 分支变 |
| 常数形态 | 每分支独立静态常数表 | 常数由 khronos 旋转派生 |
| 输出组装 | 直接 20B | 32B 折叠 16B core + 4B khronos 尾 |

### 差异三：Perseus 启用

41.1 起启用新一代设备报告 `X-Perseus`，核心字段是：

- **FL**：从 SDK 启动状态确定性派生的特征链；
- **KD**：SDK 进程内的键值状态，参与会话校验。

## 为什么不能混用

原文给出了最关键的实战结论：

> 两个版本的算法不能混用。旧版用内容选分支、新版用 khronos 选分支——如果请求走 41.2 版本号但 field13 用旧版派生，服务端按新版规则重算必然不一致；反之亦然。

这不是“兼容性问题”，而是**直接失败**：

- 请求声明 41.2；
- field13 却按 40.x 的规则选分支；
- 服务端按 41.2 重算，得到不同的 slot；
- 摘要不同，校验失败。

## 版本配置的作用

原文提到：**41.1.0 起的版本配置同时决定了 Medusa 与 Perseus 走哪套链路**。

这意味着版本号不是“一个请求头字段”，而是一个**全局开关**：

- 它决定 Medusa 用短帧还是长帧；
- 决定 field13 用内容选分支还是 khronos 选分支；
- 决定 Perseus 是否启用、走哪套 FL / KD 逻辑。

<div class="callout warn"><span class="callout-title">⚠️ 实现提醒</span>
不要把“版本号”当成单纯的字符串拼接。它应该映射到一套完整的算法配置，并在整个会话内保持一致。
